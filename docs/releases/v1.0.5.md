**Applying to this project the rules it applies to a cluster — and fixing the `update` path that nothing had ever exercised.**

v1.0.4 shipped `attest` and the audit report. This release is about the plumbing underneath: a feature that was broken in a way no test could see, reports that were written world-readable, and a release pipeline that trusted exactly the kind of moving pointer this tool refuses to trust anywhere else.

## `update` installed scanners that `doctor` could not see

`tatar-kuber update` unpacks an archive into `~/.tatar-kuber/tools/<name>/` and leaves the binary inside that directory. `toolexec.Resolve` looked for `~/.tatar-kuber/tools/<name>` as a **file** and rejected a directory.

So every scanner installed by `update` was invisible to `doctor` and to every live scan. One command said "installed", the next said "not installed", and neither returned an error.

It survived because the path had never run anywhere. CI installs its scanners with each project's own `install.sh`, straight onto `PATH`, so `Resolve` always found them the easy way; the lock-driven install existed only in tests with a fabricated layout. `Resolve` now checks the file, then `<tools>/<name>/<name>`, then walks the directory by name — the same shallowest-match rule `update` uses when it installs. If you installed scanners with `update` on v1.0.4, re-run `doctor` after upgrading; nothing needs reinstalling.

## Reports are written owner-only

v1.0.4 tightened `scan-result.json` and the raw scanner output to `0600`, on the grounds that a scan result is a list of a cluster's weaknesses. The reports stayed at `0644`, because `os.Create` means `0666 & umask`.

The hardening had reached the machine-readable copy and stopped at the human-readable one — the file that gets emailed, archived and handed to a client. `html`, `audit`, `sarif` and `json` are now created `0600`, and the PDF is chmodded after the converter writes it. A file that already exists keeps the permissions you gave it.

## The release pipeline no longer trusts moving tags

This project pins every scanner by SHA256 and refuses to install one it cannot verify. Its own release job, meanwhile, ran three third-party Actions at mutable major tags with `contents: write` and `packages: write`.

A tag is a pointer its owner can move, and in March 2025 that was done to `tj-actions/changed-files` to leak secrets out of thousands of repositories. What makes it sharper here: `checksums.txt` and the SBOM are produced by those same steps, so a compromised Action would publish a backdoored binary **with a checksum that matches it**. Verifying the checksum would confirm the forgery.

All five third-party Actions are pinned to commit SHAs with the readable version beside each. `actions/*` and `github/codeql-action` stay on major tags — compromising GitHub's own namespace is a different class of event. `.github/dependabot.yml` now raises updates weekly, because a pin nobody revisits is a permanently vulnerable dependency; pinning also made existing staleness visible, which was the point.

## The regression net moved to the side it guards

The Lab corpus is a regression baseline, but its workflow only ran on pushes to the Lab. An engine change that broke mapping, dedup, rollup or scoring left the Lab silent — the net was hanging beside the thing it was supposed to catch.

The Lab now runs inside this repository's CI on every push. The step also asserts that every scanner contributed at least one finding: `verify-lab` compares the control set and per-severity counts, which cannot see one scanner's contribution vanishing when another covers the same control — exactly how v1.0.0 shipped with Trivy contributing nothing and healthy totals.

## The pin is now what CI exercises

`real-cluster.yml` and `static-scan.yml` install scanners with each project's installer, which fetches **latest**. That is deliberate — it is how upstream breakage is found the day it lands — but it meant `tools.lock.yaml` governed only what a user gets from `update`, and nothing exercised that at all.

Both now run. A second job installs from the shipped lock with `tatar-kuber update`, asserts the installed version is the pinned one, asserts `doctor` can see it, and runs `scripts/check-trivy-rules.py` to confirm the pinned trivy's rule IDs still resolve to the controls they are mapped to. That job found the `Resolve` bug above on its first run.

## Pins moved, after the mappings were checked

trivy 0.74.0 → 0.76.1, kubescape 4.0.15 → 4.0.17, checkov 3.3.20 → 3.4.0 (still unpinned by design). Eight checksums, each read from the release's own published checksum file.

trivy proved why moving a pin is not a version edit: it embeds its rules in the binary, and 0.76.1 emits `KSV-0001` where 0.74.0 emitted `AVD-KSV0001`, with `AVDID` empty. Before the pin moved, 0.76.1 was downloaded, run against the Lab manifests, and every rule ID it produced was resolved through the registry by hand — 17 of 21 map to the control their title describes, and the four that do not are reported as `unmapped_rules` rather than lost. The shape change is absorbed by `NormalizeRuleID`, the fix that came out of the v1.0.0 incident.

## Drift is reported where it means something

The drift check raised on plain inequality, and using it disproved that within half an hour: while the pins were being verified and moved, all three projects published again. "Behind upstream" is permanently true for projects that release constantly, an issue raised on it never closes, and a permanently open issue is the same failure as a Security tab with twenty alerts nobody reads.

A pin is a *reviewed* version, not the newest one. The check now raises on a **minor or major** gap — the class of release that can move rule IDs — or on a pin older than **90 days**. A patch published this morning is printed as information.

**kubescape's rules are watched separately**, because kubescape downloads its policy library at scan time: pinning the binary pins nothing about the meanings, and the rule set can change with no version bump. A daily job compares every mapped `C-id` against the published library. It found two renames on its first run (`C-0210`, `C-0262`); both kept their meaning, so no mapping changed — and nobody would have noticed either.

## Documentation

The README's security section still claimed the suggested ClusterRole read "Secret *metadata* only, never secret values". v1.0.4 removed that permission entirely, and the reason was that this exact promise is impossible in RBAC. The documentation was advertising the old version of the thing it had fixed.

# Монголоор

**Кластерт тавьдаг шаардлагаа энэ төсөл дээрээ хэрэглэх — мөн хаана ч ажиллаж байгаагүй `update`-ийн замыг засах.**

v1.0.4 нь `attest` болон аудитын тайланг авчирсан. Энэ хувилбар нь доорх суурийн тухай: ямар ч тест харж чадахгүй байдлаар эвдэрсэн боломж, нийтэд уншигдахаар бичигддэг тайлан, мөн энэ хэрэгсэл өөр хаана ч итгэдэггүй төрлийн хөдөлгөөнт заагчид итгэдэг байсан release зам.

## `update` суулгасан scanner-ийг `doctor` олдоггүй байв

`tatar-kuber update` нь архивыг `~/.tatar-kuber/tools/<name>/` **дотор** задалж, binary-г тэнд үлдээдэг. `toolexec.Resolve` нь `~/.tatar-kuber/tools/<name>`-ийг **файл** гэж хайж, сан байвал татгалздаг байв.

Тиймээс `update`-ээр суулгасан scanner бүр `doctor` болон амьд scan-д үл үзэгдэх байсан. Нэг команд "суулгалаа" гэж хэлээд нөгөө нь "суугаагүй" гэж хэлнэ, аль нь ч алдаа буцаахгүй.

Яагаад амьд үлдсэн бэ: тэр зам хаана ч ажиллаж байгаагүй. CI нь scanner-уудаа төслүүдийн өөрсдийнх нь `install.sh`-ээр шууд `PATH` руу суулгадаг тул `Resolve` тэднийг хялбар замаар олдог байв; lock-оос суулгах зам нь зөвхөн зохиомол байрлал бүхий тестэд л байсан. `Resolve` одоо: файл → `<tools>/<name>/<name>` → сангаар нь нэрээр хайх. v1.0.4 дээр `update`-ээр scanner суулгасан бол шинэчилсний дараа `doctor`-оо дахин ажиллуул; дахин суулгах шаардлагагүй.

## Тайлан зөвхөн эзэмшигчид уншигдахаар бичигдэнэ

v1.0.4-д `scan-result.json` болон түүхий гаралтыг `0600` болгосон — учир нь scan-ийн үр дүн бол кластерын сул талуудын жагсаалт. Гэтэл тайлан нь `0644` хэвээр үлдсэн, учир нь `os.Create` нь `0666 & umask` өгдөг.

Хамгаалалт нь машины уншдаг хувилбарт хүрээд зогссон, харин хүний уншдаг — имэйлээр явдаг, архивт үлддэг, үйлчлүүлэгчид өгдөг — хувилбар нь нээлттэй хэвээр байв. `html`, `audit`, `sarif`, `json` дөрвүүлээ одоо `0600`-аар үүснэ, PDF-ийг хөрвүүлэгч бичсэний дараа chmod хийнэ. Аль хэдийн байгаа файлын эрхийг өөрчлөхгүй.

## Release зам хөдөлгөөнт tag-д итгэхээ больсон

Энэ төсөл scanner бүрийг SHA256-аар пиннэж, баталгаажуулж чадахгүй хэрэгслийг суулгахаас татгалздаг. Гэтэл өөрийн release ажил нь гуравдагч этгээдийн гурван Action-ыг хөдөлгөөнт major tag-аар, `contents: write` ба `packages: write` эрхтэйгээр ажиллуулж байв.

Tag бол эзэмшигч нь зөөж чадах заагч бөгөөд 2025 оны 3-р сард `tj-actions/changed-files` дээр яг тэгж мянга мянган repo-гийн нууц алдагдсан. Энд илүү хурц байсан шалтгаан: `checksums.txt` ба SBOM-ыг ЯГ ТЭР алхмууд үүсгэдэг тул эвдэрсэн Action нь backdoor-той binary-г **түүнд таарсан checksum-тай** нийтэлнэ. Checksum тулгах нь хуурмагийг нь баталж өгнө.

Гуравдагч таван Action бүгд commit SHA-гаар пиннэгдэж, хажууд нь уншигдах хувилбар бичигдсэн. `actions/*` ба `github/codeql-action` нь major tag-аар үлдэв — GitHub-ийн өөрийнх нь нэрийн талбарыг эзэмдэх нь өөр ангиллын халдлага. `.github/dependabot.yml` нь долоо хоног тутам шинэчлэлт ирүүлнэ, учир нь хэн ч эргэж хардаггүй пин бол үүрд эмзэг хамаарал; пиннэх үйлдэл нь байсан хоцролтыг мөн ил гаргасан нь зорилго байсан.

## Регрессийн тор барих ёстой талдаа шилжив

Lab корпус бол регрессийн суурь мөртлөө түүний workflow зөвхөн Lab руу push хийхэд ажилладаг байв. Engine дээрх өөрчлөлт зураглал, dedup, rollup, оноололтыг эвдсэн ч Lab чимээгүй хэвээр — тор нь барих ёстой зүйлийнхээ хажууд өлгөөстэй байсан.

Lab одоо энэ repo-гийн CI дотор push бүр дээр ажиллана. Мөн scanner бүр дор хаяж нэг олдвор оруулсан эсэхийг шаардана: `verify-lab` нь control-ийн олонлог ба severity тус бүрийн тоог тулгадаг тул нэг scanner-ийн хувь нэмэр алга болохыг — өөр scanner тэр control-ыг хамарч байвал — харахгүй. v1.0.0 яг ингэж Trivy юу ч оруулаагүй атлаа эрүүл тоотой гарсан.

## Pin нь одоо CI-ийн шалгадаг зүйл боллоо

`real-cluster.yml` ба `static-scan.yml` нь scanner-уудыг төслүүдийн суулгагчаар татдаг — тэр нь **хамгийн сүүлийнх**. Энэ нь зориуд: upstream эвдэрсэнийг тэр өдөрт нь олдог цорын ганц зам. Гэхдээ үүний улмаас `tools.lock.yaml` нь зөвхөн хэрэглэгчийн `update`-д үйлчилж, түүнийг хэн ч шалгадаггүй байв.

Одоо хоёулаа ажиллана. Хоёр дахь job нь shipped lock-оос `tatar-kuber update`-ээр суулгаж, суусан хувилбар нь пиннэсэнтэй таарч байгааг, `doctor` түүнийг харж байгааг шалгаад, `scripts/check-trivy-rules.py`-аар пиннэсэн trivy-ийн rule ID-ууд зурагдсан хэвээр эсэхийг батална. Тэр job дээрх `Resolve`-ийн алдааг эхний ажиллалтаараа илрүүлсэн.

## Pin-үүд зураглал шалгасны дараа хөдөлсөн

trivy 0.74.0 → 0.76.1, kubescape 4.0.15 → 4.0.17, checkov 3.3.20 → 3.4.0 (зориуд пиннэгдээгүй хэвээр). Найман checksum, тус бүр нь release-ийн өөрийнх нь нийтэлсэн файлаас.

Pin хөдөлгөх нь хувилбарын засвар биш гэдгийг trivy өөрөө нотлов: дүрмээ binary дотроо шигтгэдэг бөгөөд 0.76.1 нь 0.74.0-ийн `AVD-KSV0001`-ийг `KSV-0001` болгож, `AVDID`-г хоосон үлдээжээ. Pin хөдлөхийн өмнө 0.76.1-ийг татаж, Lab-ийн манифест дээр ажиллуулж, гаргасан rule ID бүрийг бүртгэлээр гараар шийдэв — 21-ээс 17 нь гарчигтаа тохирох control руу зурагдаж, үлдсэн 4 нь `unmapped_rules` болж ил гарна, алдагдахгүй. Хэлбэрийн өөрчлөлтийг `NormalizeRuleID` шингээж байна — v1.0.0-ийн ослоос төрсөн тэр засвар.

## Хоцролтыг утга учиртай үед нь мэдээлнэ

Drift шалгалт энгийн тэнцүү бишээр дохио өгдөг байсныг хэрэглэж үзэхэд хагас цагийн дотор буруу нь нотлогдов: pin-үүдийг шалгаж хөдөлгөх зуур гурван төсөл бүгд дахин гарлаа. Байнга release хийдэг төслүүдийн хувьд "хоцорсон" нь үүрд үнэн, тэр дээр нээсэн issue хэзээ ч хаагдахгүй — хэн ч хардаггүй 20 анхааруулгатай самбартай ижил эвдрэл.

Pin бол **хянагдсан** хувилбар, хамгийн шинэ нь биш. Одоо **minor/major** зөрүү (rule ID өөрчлөгдөж болох ангилал) эсвэл **90 хоногоос** хуучирсан pin дээр л дохио өгнө. Өглөө гарсан patch нь мэдээлэл болж хэвлэгдэнэ.

**kubescape-ийн дүрмийг тусад нь харж байна**, учир нь kubescape бодлогын сангаа scan хийх үед татдаг: binary-г пиннэх нь утгыг пиннэдэггүй, дүрмийн багц хувилбар солигдолгүйгээр өөрчлөгдөж болно. Өдөр тутмын ажил зураглагдсан `C-id` бүрийг нийтлэгдсэн сантай тулгана. Эхний ажиллалтаараа хоёр нэрийн өөрчлөлт илрүүлэв (`C-0210`, `C-0262`); хоёулангийнх нь утга хэвээр тул зураглал өөрчлөгдөөгүй — бас хэн ч анзаарахгүй байсан.

## Баримт

README-гийн аюулгүй байдлын хэсэг санал болгож буй ClusterRole нь "Secret-ийн ЗӨВХӨН metadata, утгыг хэзээ ч уншихгүй" гэж бичсэн хэвээр байв. v1.0.4 тэр эрхийг бүр мөсөн хассан бөгөөд шалтгаан нь яг энэ амлалт RBAC дээр боломжгүй байсан явдал. Баримт нь зассан зүйлийнхээ хуучин хувилбарыг сурталчилсаар байжээ.
